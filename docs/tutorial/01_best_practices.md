# 1章 ベストプラクティス解説

2章から実際にテストを書き始める前に、Playwright でテストを自動化するときに大切な4つの考え方を先に紹介します。
この章は読むだけの章です。コマンドの実行やプロジェクトの変更はありません。ここで「なぜそうするか」を知っておくと、後の章で出てくる書き方の意味が分かりやすくなります。

## この章の前提知識

- 0章で学習用プロジェクトを作り、`dotnet test` が成功したこと
- 「テスト」とは、プログラムが期待どおりに動くかを自動で確かめるコードである、というおおまかなイメージ

## 1. テストケースの独立性

**各テストは、他のテストの結果や実行順序に頼らず、それ単体で成功・失敗が決まるように書きます。**

悪い例は「テストAでデータを保存し、テストBはそのデータが残っている前提で読み込む」という書き方です。テストBだけを実行したり、実行順が入れ替わったりすると、テストBはコードに問題がなくても失敗します。原因の切り分けも難しくなります。

このリポジトリの完成版テストでは、次のように独立性を守っています。

- 「送信して結果を確認するテスト」と「読み込んで復元を確認するテスト」は別々のメソッドです。読み込み側のテストは、送信側のテストが保存したデータを当てにせず、**自分で送信してから**読み込みます（9章で扱います）。
- テストごとに新しいブラウザの状態（Cookie などを含む）を用意し、前のテストの状態を持ち越さないようにしています（8章で扱います）。

## 2. 待機処理の書き方

Webページは、ボタンを押してからサーバーの応答が返り、画面が書き換わるまでに少し時間がかかります。そこで、つい次のように「一定時間待つ」コードを書きたくなります。

```csharp
// 悪い例: 「たぶん2秒あれば終わるだろう」と決め打ちで待つ
await Task.Delay(2000);
```

これには2つの問題があります。

- PCが遅いときや負荷が高いときは2秒で終わらず、テストがたまに失敗する（不安定なテスト）
- 速く終わるときも必ず2秒待つので、テスト全体が無駄に遅くなる

Playwright では、`FillAsync`（入力）や `ClickAsync`（クリック）といった**操作系のメソッドが、要素が表示されて操作できる状態になるまで自動的に待ってから操作します**（自動待機）。また、`Assertions.Expect(...)` で書く検証は、条件を満たすまで繰り返し確認してくれます。4章で実際にこれらを使い、固定時間の待機を一切書かずにテストを組み立てます。

注意点が2つあります。

- 3章で使う `CountAsync()`（要素の数を数える）や `IsVisibleAsync()`（表示されているか調べる）は、**待たずに「今この瞬間の状態」を返す**メソッドです。操作系メソッドのような自動待機はしないため、「自動待機の例」ではありません。
- 完成版テストには、テスト開始前にサーバーの起動完了を「HTTPで繰り返し問い合わせて」待つ処理があります（8章）。これはテストを実行する側のプログラムが自分で行う待機であり、Playwright の要素に対する自動待機とは別の仕組みです。

## 3. ロケーターの選び方

ロケーターとは、画面上の要素を探すための「目印」です。次のような目印は、テストを壊れやすくします。

```csharp
// 悪い例1: 見た目用のCSSクラス名に頼る → デザイン変更でクラス名が変わると壊れる
page.Locator(".field input");

// 悪い例2: 要素の位置（何番目か）に頼る → 入力欄が1つ増えると別の要素を指してしまう
page.Locator("input").Nth(0);
```

そこで、このプロジェクトでは**テスト専用の属性 `data-testid`** をHTMLに付け、それを目印にすることにしました。`data-testid` は見た目にも動作にも影響しないので、デザインが変わってもテストは壊れにくくなります。

```html
<!-- サンプルアプリの index.html より。data-testid="text-input" がテスト用の目印 -->
<input type="text" id="text-input" name="text" data-testid="text-input" autocomplete="off">
```

完成版テストでは、目印の値（`text-input`、`slider`、`submit-button` など）を `FormTestIds` という定数クラスにまとめて管理しています。具体的な使い方は3章で学びます。

## 4. テストケースのパラメータ化の考え方

「空文字を入れた場合」「1000文字の場合」「1001文字の場合」…と入力パターンごとにテストメソッドを書くと、次のような問題が起きます。

- 操作と検証の手順はどのテストも同じなのに、コードが何度も複製される
- 新しいパターンを試すたびに、テストメソッドそのものを追加・修正しなければならない

そこで、**「入力値と期待値の組」をデータとして一か所にまとめ、テストの手順（メソッド）とは分けて管理します。** 手順は1つだけ書き、データの数だけ繰り返し実行させるイメージです。

```csharp
// イメージ: 1件のテストケースを「データ」として表す（完成版の FormValuesTestCase 型に相当）
// 名前・入力値・期待する結果をひとまとめにしておけば、パターンの追加はデータを1行足すだけで済む
("文字数ちょうど1000", new string('a', 1000), 保存に成功するはず)
("文字数1001",        new string('a', 1001), 保存が拒否されるはず)
```

上のコードは考え方を示すための擬似コードで、このままでは動きません。完成版テストでは `FormValuesTestCase` というレコード型でこれを表現しており、7章で NUnit の `[TestCaseSource]` と組み合わせて実際に動かします。
