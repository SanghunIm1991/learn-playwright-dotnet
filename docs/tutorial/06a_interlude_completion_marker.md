# 間章 アプリ側に「処理完了の目印」を置く方法

> **この章は読み飛ばしても構いません。** 7章以降は、この章の内容を使わずに進めます。
> 5〜6章の書き方（応答待ち＋期待する値になるまで待つアサーション）で足りない場面があることと、そのときの補助的な手段を知っておきたい人向けの章です。

## この章の前提知識

- 6章: `ClickSubmitButtonAsync` / `ClickLoadButtonAsync`（クリック＋応答待ち）と、`ExpectFormValuesAsync` / `ExpectMessageTypeAsync`（期待どおりになるまで待って確かめる）
- 5章: `RunAndWaitForResponseAsync`、`ToHaveValueAsync`、`InputValueAsync()` は待たずに今の値を返すこと
- 4章: メッセージ欄の種類が `message--success` などのクラスで表されること

## 5〜6章の書き方で足りない場面

5〜6章の書き方は、「操作の後、画面が**期待する状態に変わる**」ことを前提にしています。変わるまで待ち、変わったら合格です。逆に言うと、**操作の前から画面が期待する状態だった場合**には、待つべき変化がありません。

### 場面1: 期待する値が、操作前の画面と同じ

たとえば、プルダウンの初期値は `apple` です。「`apple` を保存 → ページを開き直す → 読み込む → `apple` に戻ったか」を確かめると、開き直した直後から画面はすでに `apple` なので、`ToHaveValueAsync("apple")` は読み込みの反映を待たずにすぐ合格します。

`ClickLoadButtonAsync` はサーバーの応答が返るまで待ちますが、アプリが受け取った値を画面に反映するのは応答を受け取った**後**です。そのため、「応答が返った」時点では画面がまだ書き換わっていないことがあります。

これは、期待値の**一部の項目**が操作前の画面と同じだけでも起こります。`ExpectFormValuesAsync` はテキスト → スライダー → プルダウン → ラジオの順に確かめます。たとえば9章の `BND-TEXT-EMPTY`（テキストの期待値が空文字）では、最初のテキストの確認が、反映前の空の画面を見てすぐ合格します。反映を待つのは、初期値と違う値を期待する次のスライダーの確認からです。期待値がすべて操作前の画面と同じなら、すべての確認が反映前に合格してしまいます。

なお、この場面には性質の違う2つの問題が含まれています。

- **タイミングの問題**: 反映前の画面を確かめてしまう。下で紹介する目印を使えば、反映まで待ってから確かめられる。
- **区別できない問題**: 反映を待ってから確かめても、期待値が操作前の画面と同じなら、「正しく戻った」のか「何も変わらなかった」のかは画面から区別できない。これは待ち方では解決せず、次の「まず検討すること」のようにテストの手順を工夫する必要がある。

### 場面2: 同じ表示が続く

同じページで送信を2回続けると、1回目の後にはすでに「保存しました。」（`message--success`）が表示されています。2回目の送信の後に `ExpectMessageTypeAsync(page, "success")` を呼ぶと、2回目の結果を待たずに、1回目の表示を見てすぐ合格してしまいます。

### 場面3: 「待たずに読む」書き方で、まとめて比べたい

`Assertions.Expect` は、最初に失敗した項目でテストを止めます。4つの値を `InputValueAsync()` などで一度に読み取り、NUnit の `Assert.Multiple` で「ずれている項目をまとめて報告する」書き方をしたい場合もあります。ただし `InputValueAsync()` は待たないので、読む前に「画面の書き換えまで終わっている」ことが確実でなければなりません。上で見たとおり、応答待ちだけではそこまでは保証されません。

## まず検討すること

足りない場面に出会ったら、アプリに手を入れる前に、次のような方法で解決できないか考えます。

- **テストの手順・データを工夫して、操作の前後で必ず画面が変わるようにする**: 次のような方法があります。
  - 操作の前に、画面の値を期待値とわざと違うものにしておく（例: 読み込みボタンを押す前にテキストへ `"読み込み前"` と入れておき、空文字に戻ることを確かめる）。タイミングの問題と区別できない問題の両方を解決できる
  - 確かめる順番の最初に、「操作直前の画面」と違う値を期待する項目を置く。反映を待ってから残りを確かめられる（区別できない問題は残る）
  - 同じページで同じ操作を2回続けない
- **利用者にも意味のある表示を使う**: 処理中はボタンを押せなくする、「処理中…」と表示する、`aria-busy` 属性（「この部分は更新中」と支援技術に伝える属性）を付ける、などです。利用者のための表示であれば本番コードに入っていても不自然ではなく、テストはその表示が消えるのを待てます（このサンプルアプリには、こうした表示はありません）。

## 補助的な手段: 処理完了の目印

それでも難しい場合の手段として、**アプリ側に「処理が終わった」ことを示す目印を置き、テストはその目印の変化を待つ**方法があります。このサンプルアプリには、この目印が用意されています。

### アプリ側の目印

フォーム要素の `data-request-count` 属性です。初期値は `0` で、送信・読み込みの処理が（成功・失敗を問わず）終わるたびに 1 ずつ増えます。

```html
<form id="user-form" data-testid="form" data-request-count="0" novalidate>
```

`app.js` では、ボタンの処理（通信と画面の書き換え）がすべて終わった後で、この数を増やしています。

```javascript
// 処理完了ごとに data-request-count を1増やす
function markRequestCompleted(formElement) {
  if (formElement) {
    const current = Number(formElement.dataset.requestCount || '0');
    formElement.dataset.requestCount = String(current + 1);
  }
}

// 送信ボタンの処理（handleSubmitButtonClick）が終わってから目印を更新する
deps.submitButton.addEventListener('click', async (event) => {
  await handleSubmitButtonClick(event, deps);
  markRequestCompleted(deps.formElement);
});
```

### テスト側の待ち方

「押す前の値を覚えておき、値が変わるまで待つ」と書きます。

```csharp
var form = page.GetByTestId("form");

// 押す前の処理完了回数を読んでおく（属性がなければ "0" とみなす）
string before = await form.GetAttributeAsync("data-request-count") ?? "0";

await page.GetByTestId("load-button").ClickAsync();

// 属性の値が「押す前の値ではなくなる」まで待つ（Not を付けると「〜でなくなるまで」になる）
await Assertions.Expect(form).Not.ToHaveAttributeAsync("data-request-count", before);

// ここまで来れば、画面の書き換えまで終わっている。待たない読み取りを使っても安全
string select = await page.GetByTestId("select").InputValueAsync();
Assert.That(select, Is.EqualTo("apple"));
```

目印は「画面の書き換えまで含めて処理が終わった」ことを表すので、場面1〜3のどれにも使えます。ただし場面1のうち「区別できない問題」は、目印を使っても解決しません。

## この方法の代償

- **テストのためだけの仕組みが本番コードに入ります。** 利用者にとっては意味のない属性で、アプリのコードを読む人に「これは何のためか」を説明する必要があります（`index.html` と `app.js` には、そのためのコメントを付けています）。
- **アプリを自分たちで変更できる場合にしか使えません。** 他社のサイトなど、手を入れられないアプリのテストでは使えません。
- **目印の更新を忘れると、テストが待ち続けます。** たとえばボタンを1つ追加したときに目印の更新を入れ忘れると、そのボタンのテストはタイムアウトで失敗します。
- **目印は「終わった」ことしか表しません。** 成功したか失敗したかは、これまでどおり画面に見える結果（メッセージ欄など）で確かめる必要があります。

このため、Playwright でよく使われるのは5〜6章の書き方で、この方法は「それでは足りないときの補助的な手段」という位置づけです。

## 完成版テストとの関係

リポジトリの完成版テスト（`tests/LearnPlaywright.Tests`）は、場面3の書き方を選んでいるため、この目印を使っています。

| 項目 | 6章のヘルパー | 完成版の `TestData/FormPageHelpers.cs` |
|---|---|---|
| ボタンを押した後の待ち方 | サーバーの応答を待つ（`RunAndWaitForResponseAsync`） | `data-request-count` が変わるまで待つ |
| 値の確かめ方 | `ExpectFormValuesAsync`（期待どおりになるまで待つ） | `GetFormValuesAsync` で4つの値を読み、`Assert.Multiple` でまとめて比べる |
| メッセージの確かめ方 | `ExpectMessageTypeAsync`（期待どおりになるまで待つ） | `GetMessageAsync` で読み取り、種類を `Assert.That` で比べる |

どちらも「固定時間では待たない」という点は同じです。9章で完成版テストを読み比べるときの参考にしてください。

## この章のまとめ

- 5〜6章の書き方は「画面が期待する状態に変わる」ことを待つ。操作前から期待どおりの画面や、同じ表示が続く場面では、待つべき変化がない。期待値の一部の項目だけが操作前と同じ場合でも、確かめる順番によっては反映前に合格する
- 期待値が操作前の画面と同じ項目は、待ち方にかかわらず「正しく戻った」のか「変わらなかった」のかを画面から区別できない
- まずはテストの手順・データの工夫（操作前に画面をわざと違う値にしておく等）や、利用者にも意味のある表示で解決できないか考える
- 補助的な手段として、アプリ側に処理完了の目印（このサンプルでは `data-request-count`）を置き、その変化を待つ方法がある。テストのための仕組みが本番コードに入るなどの代償がある

## この章で出てきた書き方

| 書き方 | 意味 |
|---|---|
| `await form.GetAttributeAsync("data-request-count") ?? "0"` | `GetAttributeAsync` は属性の値を読む（属性がなければ `null`）。`A ?? B` は「A が null なら B を使う」 |
| `Assertions.Expect(form).Not.ToHaveAttributeAsync(...)` | `Not` を付けると「〜でなくなるまで」待つ確認になる |
| `Assert.Multiple(() => { ... })`（NUnit） | 中の `Assert.That` が途中で失敗しても残りも確かめ、ずれている項目をまとめて報告する |
| JavaScript の `const current = ...` | 後から入れ替えない変数の宣言 |
| JavaScript の `A \|\| '0'` | A が空（属性がない等）なら `'0'` を使う |
| JavaScript の `formElement.dataset.requestCount` | `data-request-count` 属性の値を読み書きする書き方（`data-` の後ろがつながった名前になる） |
