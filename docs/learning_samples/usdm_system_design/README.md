## USDMの書き方の作法（要点）

USDM（Universal Specification Describing Manner）は、要求を**「要求」と「仕様」の2階層に分けて書く**表記法です。この資料で守っている作法を、自分の言葉でまとめます。

### 1. 要求と仕様を分ける

| | 要求 | 仕様 |
|---|---|---|
| 書くこと | 利用者が**何をしたいか・何ができるべきか** | 要求を満たすために**システムが具体的に何をするか** |
| 文の形 | 「〜できる」「〜しない」など、振る舞いを表す動詞で書く | 「〜すること」と、検証できる形で書く |
| 例 | 利用者は、送信ボタンで入力内容を保存できる | テキストが1000文字を超える場合は保存を拒否すること |

要求の主語は、利用者（「学習者は〜できる」）とするのが基本です。ただし、利用者の操作と直接結び付かない性質（安全性や同時実行への強さなど）は、「システムは〜しない」のようにシステムを主語にして書きます。どちらの場合も、仕様より一段抽象的な「振る舞い・性質」を表す点は同じです。

要求だけでは「どこまでやればよいか」が決まらず、仕様だけでは「何のためか」が分かりません。両方を**親子関係**でつなぐことで、仕様の漏れ（要求があるのに仕様がない）や、余計な仕様（どの要求にも属さない）に気付けます。

### 2. すべての要求に「理由」を書く

理由は、要求の**解釈の幅を狭める**ために書きます。たとえば「ブラウザごとに利用者を区別する」という要求も、理由が「ログインなしで試せるように」なのか「厳密な本人確認のため」なのかで、必要な仕様（Cookieで十分か、認証が必要か）が変わります。

必要に応じて「説明」を添え、用語の定義や前提、範囲外のことを補足します。

### 3. 要求は階層化し、仕様はグループで整理する

- 大きな目的（上位要求）を、具体的な場面の要求（下位要求）に分解します。1つの上位要求の下に下位要求が多すぎる場合は、分け方を見直す合図です。
- 1つの下位要求に仕様がたくさんぶら下がる場合は、`<送信内容>`・`<入力検証>`のように**グループ名**を付けて並べます。仕様の抜けを見つけやすくなります。

### 4. 仕様は「確かめられる」粒度で書く

「適切に」「十分に」「必要に応じて」といった言葉は、人によって解釈が分かれるので使いません。数値・条件・結果を明記し、そのままテストケースにできる形を目指します。

### 5. リバースエンジニアリングで書くときの作法

実装から要求を起こす場合は、次の順番で進めると整合が取りやすくなります。

1. **仕様を先に集める**: コードから、事実として確かめられる振る舞い（値の範囲、エラー時の動き等）を拾う。この資料では各仕様に「根拠」として実装箇所を書いている
2. **仕様をまとめて下位要求を起こす**: 同じ目的に役立つ仕様を束ね、「利用者は〜できる」という形に言い換える
3. **理由を類推する**: その要求がなぜ必要かを、題材の目的（Playwrightの学習）から推し量って書く
4. **上位要求で括る**: 下位要求を、利用者の大きな目的ごとにまとめる
5. **矛盾を確かめる**: どの要求にも属さない仕様、仕様が1つもない要求がないかを見直す。あわせて、**仕様が親の要求の「理由」に本当に役立っているか**、下位要求が上位要求の理由に役立っているかも確かめる。役立っていなければ、置き場所の誤りなので、別の要求を立てて移す（この資料でも、初版の独立レビューで2件見つかり、UR-05・SR-03-05を新設した。01の4章参照）
6. **実装との差異を記録する**: 類推した意図と実装がずれている箇所が見つかったら、黙って仕様を実装に合わせるのではなく、差異として記録する。仕様の範囲を実装に合わせて絞る場合も、何をどう絞ったかを残す（01の4章）
